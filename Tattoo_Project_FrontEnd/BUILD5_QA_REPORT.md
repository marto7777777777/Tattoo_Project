# InkRoute iOS Build 5 — stability/privacy fix

## Root cause
The supplied Apple diagnosis identifies a TCC SIGABRT caused by missing NSCameraUsageDescription. The actual App target uses App/Info.plist in both configurations; that source file lacked camera and photo usage descriptions. This archive has no @capacitor/camera dependency or Camera.getPhoto calls. The AI reference control is HTML input[type=file]; WKWebView presents Apple's camera/photo chooser. JavaScript cannot catch a TCC process termination or inspect the permission outcome of that chooser.

## Final Image Pipeline Cleanup

1. Duplicate AI processing was in CreateAiTattooPage.chooseReference and aiTattooApi.projectForm. 3. Basic validation permits empty MIME, rejects empty/non-Blob/unsupported declared MIME. Decode failure (including zero dimensions) occurs outside the optimization catch and cannot return an original. After successful decode, canvas/transcode errors enter a separate catch. Original fallback requires size <= existing maxBytes, original dimensions within caller maxWidth/maxHeight, supported JPEG/PNG/WebP magic bytes, and agreement with any declared MIME. Signature checking alone does not establish validity: successful browser decode is also required. Originals requiring resize cannot bypass the dimension settings on optimization failure.

## First Image Selection Regression — latest patch

This section supersedes earlier handler/reset/test-count descriptions. Baseline is InkRoute_FRONTEND_iOS_Build5_AppStore_FINAL.zip.

### Evidence and root-cause limits
The reported physical iPhone symptom (camera and library sometimes need 2–3 selections) is accepted as real. This environment cannot reproduce or instrument that physical WebView. An exact device-level root cause is therefore NOT established, and this patch must be retested on the affected iPhone before calling the symptom resolved.

Verified code defect: in src/utils/images.js decodeImage's HTML Image fallback, URL.revokeObjectURL ran in finally immediately after onload, before the returned image was drawn to canvas. Large phone photos requiring resize could then fail processing and could not use the bounded original fallback. The URL now stays alive through drawing and asynchronous encoding; decoded.close() revokes it in the existing outer finally. Decode failures revoke immediately. A mock that invalidates the backing image when its URL is revoked reproduces the premature-release defect against the previous source. This is a resource lifetime fix, not proof that every WebKit version invalidates an already loaded image upon revocation.

Related defensive handler change: CreateAiTattooPage.chooseReference previously copied the File then immediately cleared input.value. That is often valid browser code; copying File was already correct, and there is no evidence that React event pooling or a reset effect lost the result. To remove early picker-attachment release as a variable, the handler now captures input and File synchronously, retains the input value through the awaited processing, and clears the captured input in finally. No event object is accessed after await. Same-file reselection is rearmed after success/failure; Cancel does not clear previous React file/form state. The lock starts false, is checked before processing, and always clears in finally. No timer/retry/second optimization was added.

### Complete traced path
System picker -> input onChange -> captured input.files[0] -> local File -> basic validation -> createImageBitmap or HTML Image/object URL -> canvas encoding or safe original fallback -> exactly one setFile(prepared) when mounted -> existing filename/has-file UI -> same File in projectForm FormData referenceImage -> existing API request. This form has no image-thumbnail preview. No effect resets its file state; form style/placement edits only update form. Pending processing disables input/submit and successful selection is committed once. A valid fallback is returned by optimizeImageForUpload and committed by that same setter.

### Failure feedback
Cancel/empty result returns quietly and preserves prior selection. Known local invalid/unsupported/decode/dimension/output-size errors now receive their specific safe message; arbitrary optimization/native/browser exception text is not exposed. Failed replacement keeps the previous reference. Success (processed or fallback) commits a file and clears processing. Safe fallback, empty-MIME decode support, output/batch limits and no arbitrary input cap remain as in the previous final patch.

## Build 8 — confirmed oversized processed-image rejection

New physical-device evidence: screenshot shows "The optimized image is still too large. Please choose a smaller image." next to the reference picker. This identifies the helper's explicit post-encoding byte-limit rejection. It is not a picker/camera permission failure. The screenshot does not prove the actual encoder MIME or original image dimensions; WebP-to-PNG fallback is one supported failure scenario, not a measured device fact.

Root cause for this rejection path: optimizeImageForUpload resized to maxWidth/maxHeight once, then only reduced encoding quality at the same pixel dimensions. If output still exceeded the pre-existing 4.5 MiB setting, it threw. A lossless PNG fallback ignores quality; some large lossy results can also remain above the byte limit. Choosing another/smaller picture could work while the larger output was refused. This evidence supersedes the earlier speculative explanations for the reported failure.

Fix: after the existing quality attempts, perform at most eight dimension-reduction steps only while output exceeds settings.maxBytes. Each step scales both dimensions by the same calculated factor (0.5 to 0.85), rounds down with a one-pixel floor, redraws the same decoded original and encodes again. No second decode, compounded recompression of previous outputs, backend change, input cap, library/plugin or byte-limit increase. The algorithm retains output MIME/extension, including PNG transparency, and still rejects empty/unsupported output or results that cannot meet the limit. Sequential encode passes are bounded, hold only the current result in the application code and reduce canvas allocation size on each resize. Temporary native encoder/GC memory cannot be guaranteed by this source review.

The shared helper is changed because the verified size-adaptation gap is in the common encoding path. Images already fitting limits take exactly the old path. Default/caller dimensions, upload byte/batch settings and fallback validation remain unchanged. Reduction below the configured maximum happens only where the previous code rejected; it trades some resolution for accepting a supported image within the existing limit.

Tests: 17 pass. Two new tests model (1) a camera-sized 4032x3024 input whose WebP request returns oversized PNG independent of quality and (2) oversized lossy output. They verify fitting the existing byte limit; first handler invocation commits once, MIME/extension agreement, single decode, cleanup and processing reset. Running the new suite against Build 7 source yields 15 pass / 2 fail; with this patch it yields 17 pass / 0 fail. The tests mock decoding/encoding; no actual iPhone encoder or camera was run here.
